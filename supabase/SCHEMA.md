# ASANDA database design

This schema moves ASANDA from bundled JavaScript fixtures to managed PostgreSQL while keeping public sports information separate from restricted identity data.

## Core decisions

| Area | Decision |
|---|---|
| Database | Supabase managed PostgreSQL |
| Public identifiers | UUIDs and slugs; never national IDs |
| Athlete photos | Cloudinary assets referenced through `media_assets` |
| Private athlete data | `private.athlete_details`, unavailable through the public Data API |
| Authorization | Supabase Auth, application profiles, roles, and PostgreSQL RLS |
| Time values | Integer milliseconds, never formatted strings |
| Historical affiliation | Temporal `athlete_memberships`, not a club name on the athlete |
| Advertising | Fictional demo data remains in static modules for now |

## Athlete and photo relationship

```text
athletes.photo_asset_id
        |
        v
media_assets.id
  provider = cloudinary
  public_id = atleta-prueba-01
        |
        v
Cloudinary delivery URL generated by the application
```

The database stores `atleta-prueba-01`, not the transformed URL. This allows the application to request different crops and sizes without changing the athlete record.

Cloudinary assets configured as public remain reachable by anyone who knows their delivery URL, independently of Supabase RLS. Supabase controls whether ASANDA publishes that reference; withdrawing consent must also trigger removal or restricted delivery in Cloudinary when the legal requirement calls for it.

Recommended upload workflow:

1. Create the athlete and receive its UUID.
2. Upload the image to Cloudinary with an opaque public ID such as `athlete-<uuid>`.
3. Insert a `media_assets` row with `provider = 'cloudinary'` and that public ID.
4. Set `athletes.photo_asset_id` to the media row UUID.
5. Grant photo and profile consent before publishing the athlete.

Do not use an athlete name or national ID in a Cloudinary public ID. Names change; national IDs are private and leak through URLs, logs, and caches.

## Privacy boundary

Anonymous visitors can read only:

- published organizations and approved contacts;
- published athletes with active public-profile consent;
- active affiliations and disciplines for those athletes;
- published competitions and official results;
- ratified records and published awards;
- published news, videos, albums, and public media.

The exact date of birth, national ID, guardian contact, and internal notes live in `private.athlete_details`. That schema is not exposed through the Supabase Data API and is available only to trusted server-side code using the service role.

The service-role key bypasses RLS. It must never appear in React, a `VITE_*` variable, Git, screenshots, or browser requests.

## Roles

| Role | Intended access |
|---|---|
| `administrator` | Manage users, roles, and all public content |
| `editor` | Manage public sports and editorial content |
| `club_manager` | Reserved for a later organization-scoped administration flow |
| `viewer` | Authenticated read-only account |

The initial migration intentionally limits writes to administrators and editors. Club-scoped editing needs a reviewed workflow before it receives write policies.

## Athlete classification

Affiliation and competitive category are separate dimensions:

- `athlete_memberships.membership_type` stores `associated` or `federated` for a club and period.
- `athlete_category_assignments` stores the athlete's age category and effective period.
- `age_categories` is the controlled catalog: Pre Infantil A/B/C, Infantil A/B, Juvenil A/B, and Máxima.

Category assignments are historical and cannot overlap for the same athlete. Pre-infant categories are marked as not eligible for federation; database triggers reject any overlapping active federated membership regardless of which record is inserted first.

## Data not migrated blindly

- Current fixture athletes, clubs, news, videos, and albums are examples pending validation.
- Existing state records are simulated from personal-best fields and are not authoritative.
- Existing result modules contain competition cards, not individual official results.
- Exact birth dates must not remain publicly readable.
- Existing medal arrays lack event and competition provenance.
- Placeholder Unsplash, Picsum, and YouTube content is not production data.

## Derived values

Do not persist club athlete totals, album photo counts, personal-best display values, rankings, relative publication dates, or formatted times. Calculate them from authoritative rows or expose reviewed database views later.

## Future extensions

The first schema deliberately excludes medical data, billing, real advertising, live timing ingestion, and unrestricted club administration. Add them only through a reviewed migration with explicit privacy and authorization requirements.
